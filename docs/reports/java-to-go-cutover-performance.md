# Java → Go 전환 성능 평가 (익명 사례 보고서)

운영 중인 Java Scouter Server 한 대를 이 저장소의 Go 구현으로 교체한 사례의 측정 결과다. 조직·서비스·호스트를 식별할 수 있는 정보는 뺐고, 수치는 측정 조건과 함께 적었다. 통제된 benchmark가 아니라 실제 트래픽에서 관찰한 값이므로, 다른 환경에서 같은 결과가 나온다는 보장은 아니다. 통제된 비교 방법은 [성능 목표와 검증 계획](../performance.md)과 [격리 측정 절차](../validation/isolated-benchmark.md)를 따른다.

## 1. 요약

| 항목 | Java (전환 전) | Go (전환 후) |
|---|---|---|
| 메모리(RSS) | 13.9GiB (heap 12GiB 설정) | 0.9~1.4GiB (기본 설정, 부하에 따라), text cache를 8배로 올린 뒤 최대 6.6GiB |
| CPU | 2.3~2.6 core, UDP 초당 약 1.7만 datagram | 1.3 core, UDP 초당 2.2~2.5만 datagram. 5.9일 평균 1.33 core |
| OS thread | 300 | 22 |
| kernel UDP drop | 16일 누적 약 4,676만 건 | 0 (전환 뒤 약 1주, 서버 socket 계수 기준) |
| 수집 queue 초과 | 10초마다 발생 | 0 |
| 호스트 idle(같은 시간대) | 27% | 44~48% |

- Go 쪽 수치는 Java보다 높은 부하에서 측정했다.
- Agent·Client·설정 파일은 바꾸지 않았다. 서버 구현만 교체했다.
- 전환 뒤 운영 규모에서만 드러난 결함 4건을 고쳤다(5절). 그 과정에서 생긴 유실도 함께 적었다.
- 유실이 0은 아니다. 재시작 없이 운영한 5.9일 동안 UDP datagram의 약 0.0004%가 거부됐고, XLog의 0.010%가 저장 queue 초과로 저장되지 않았다(4.3절). 자정의 보관 기간 삭제가 주된 원인이며 아직 고치지 않았다.

## 2. 환경과 측정 방법

| 구분 | 내용 |
|---|---|
| 호스트 | 16 core, 메모리 125GiB. DB 서버 한 개와 공유하며, 그 DB가 CPU 4~5 core와 메모리 40GiB 이상을 쓴다 |
| 수집 대상 | Java Agent 약 700개(TCP 연결 기준), Scouter Client와 API 소비자 약 10~20개 |
| 트래픽 | 완료 transaction(XLog) 기준 하루 중 초당 4천~1.8만 건. UDP datagram은 그 약 2배 |
| 부가 기능 | Pulse 전송(Kafka, acks 0)을 서버에 내장해 함께 실행 |
| 저장 | Java DB는 압축 파일시스템, Go DB는 압축 없는 파일시스템의 새 디렉터리. 보관은 XLog 7일, profile 3일 |
| Go 실행 설정 | UDP worker 3개, UDP 수신 buffer 32MiB, 메모리 한도 12GiB |

측정 출처는 다음과 같다.

- Go: 서버의 10초 통계 줄과 `/health` JSON([감시 기준](../operations/monitoring.md)), `top`·`pidstat`·`sar`.
- Java: 전환 직전의 `top`, kernel UDP 계수(`netstat -su`), 서버 로그의 queue 초과 기록.
- 처리량은 [AGENTS.md](../../AGENTS.md)의 정의대로 완료된 XLog 수이며, datagram 수나 pack 수와 구분해 적었다.

두 서버를 같은 시각에 같은 트래픽으로 나란히 돌린 비교가 아니다. Java 값은 전환 전날 저녁, Go 값은 전환 뒤의 측정이다.

## 3. 자원 사용

### 3.1 프로세스

| 항목 | Java | Go | 조건 |
|---|---|---|---|
| RSS | 13.9GiB | 0.9GiB | Go는 XLog 초당 1.2만 건, 기본 text cache(128MiB) |
| RSS (최대 부하 시간대) | — | 1.4GiB | XLog 초당 1.4만~1.6만 건, 기본 text cache |
| RSS (cache 확대 후) | — | 4.3~6.6GiB | text cache를 1024MiB로 올린 뒤. 다 찬 직후 4.3GiB, 5일 뒤 최대 6.6GiB |
| CPU | 2.3~2.6 core | 1.3 core | Java는 UDP 초당 약 1.7만, Go는 2.2~2.5만 datagram |
| CPU (최대 부하 시간대) | — | 2.0~2.5 core | XLog 초당 1.4만~1.7만 건 |
| OS thread | 300 | 22 | |

Go의 메모리는 대부분 설정으로 정한 cache와 queue 상한에서 나온다. text cache를 8배로 올리자 cache가 다 찬 시점의 RSS가 4.3GiB가 됐고, 그 뒤 5일 동안 최대값이 6.6GiB까지 올랐다.

### 3.2 호스트 전체

같은 요일 같은 시각(오후 최대 부하 직전)의 `sar` 값이다. 공유 DB의 부하가 날마다 같지는 않으므로 참고 값이다.

| 항목 | Java 운영 중 | Go 운영 중 |
|---|---|---|
| user | 40% | 32~34% |
| system | 24% | 8~9% |
| iowait | 9% | 12~13% |
| idle | 27% | 44~48% |

system 사용률이 줄어든 폭이 가장 크다. iowait는 공유 DB의 디스크에서 나오는 값이 대부분이어서 Scouter Server 교체와 직접 연결하기 어렵다.

## 4. 처리량과 지연

### 4.1 시간대별 추이 (전환 당일 오전)

| 시간대 | XLog 평균/s | 10초 최대/s | 수집 처리 p99 | Client 응답 p99 | Pulse 전송 record/s | RSS 평균 |
|---|---|---|---|---|---|---|
| 04시 | 4,042 | 4,660 | 23µs | 61ms | 7,345 | 861MiB |
| 05시 | 4,163 | 5,419 | 25µs | 11ms | 7,489 | 844MiB |
| 06시 | 4,912 | 6,274 | 27µs | 13ms | 8,905 | 898MiB |
| 07시 | 6,959 | 9,591 | 29µs | 29ms | 12,863 | 912MiB |
| 08시 | 10,756 | 14,201 | 35µs | 61ms | 20,142 | 906MiB |
| 09시 | 11,444 | 12,834 | 31µs | 61ms | 21,452 | 922MiB |

- 이 구간에서 UDP 거부, kernel drop, 저장 queue drop, 저장 오류, Kafka 전송 실패는 0건이다.
- 부하가 2.8배로 느는 동안 수집 처리 시간과 메모리는 거의 변하지 않았다.
- 수집 처리 시간은 pack 수신부터 저장 queue 적재까지이며, 10초 구간 p99의 시간대별 중앙값이다.
- Pulse 전송 record 수는 XLog record와 profile record를 합한 값이라 XLog 수보다 많다.

### 4.2 관찰한 최대 부하

| 항목 | 값 |
|---|---|
| XLog 10초 평균 최대 | 초당 18,508건 (UDP 초당 37,735 datagram, pack 초당 46,995개). 이후 연속 운영 중 한 구간은 초당 24,956건 |

이 값은 그 환경의 최대 유입이지 서버의 한계가 아니다. 한계 측정은 [XLog 최대 처리량 측정](../validation/2026-10-17-xlog-max-benchmark.md)처럼 격리 환경에서 따로 한다.

### 4.3 재시작 없는 연속 운영 (5.9일)

마지막 수정 배포 뒤 재시작 없이 5.9일 동안 운영한 구간의 값이다. 표는 그 안의 온전한 하루 5개다.

| 일 | XLog 합계 | 평균/s | 10초 최대/s | 최대 시간대 평균/s | 수집 처리 p99(중앙값) | UDP 거부 | RSS 최대 |
|---|---|---|---|---|---|---|---|
| 1일차 | 7.64억 | 8,838 | 16,921 | 14,989 | 35µs | 252 | 6.0GiB |
| 2일차 | 6.48억 | 7,500 | 14,232 | 12,102 | 29µs | 5,519 | 6.4GiB |
| 3일차 | 8.16억 | 9,445 | 18,189 | 15,099 | 35µs | 6,603 | 6.4GiB |
| 4일차 | 7.99억 | 9,242 | 18,024 | 14,564 | 35µs | 7,554 | 6.5GiB |
| 5일차 | 8.10억 | 9,369 | 24,956 | 15,068 | 35µs | 9,933 | 6.6GiB |

| 항목 (5.9일 누적) | 값 |
|---|---|
| 수집한 XLog | 45.0억 건 |
| CPU 평균 | 1.33 core (프로세스 CPU 시간 / 경과 시간) |
| Agent 연결 | 약 700개 전부 유지, 끊김 없음 |
| kernel UDP drop, malformed, 저장 오류 | 0 |
| UDP 거부 | 39,890 datagram (유입의 약 0.0004%) |
| 저장 queue 초과 | XLog 456,380건(0.010%), profile 1,355,219건(0.031%). 저장만 누락되고 Pulse로는 전송됨 |
| service group 없이 저장된 XLog | 82,462건 (0.0018%) |
| Pulse 전송 | XLog record 42.7억 건 전송(나머지 2.3억 건은 설정한 필터로 제외), 실패 42건, 크기 한도 초과로 버린 record 21건 |
| Client 요청 | 861만 건, 연결 읽기 timeout 947건 |
| 호스트 idle(일 평균) | 65~74% |

유실은 0이 아니다. 확인한 양상은 다음과 같다.

- **자정의 UDP 거부**: 2일차부터 매일 00:00에 보관 기간이 지난 날짜 디렉터리를 지우는 동안 수집이 약 1초 멈추고, 그 구간에 4천~1만 datagram이 거부됐다(1일차 자정에는 없었다). 지우는 하루치가 클수록 늘었다. UDP 거부의 82%가 이 시각에 나왔다. 삭제를 수집과 분리하는 수정이 필요하며 아직 고치지 않았다.
- **낮 시간의 짧은 정체**: 수집 최대 지연이 약 300ms까지 오르며 수십~수천 datagram이 거부된 구간이 5일 동안 5번 있었다. 원인은 확인하지 못했다.
- **저장 queue 초과**: 누적 계수로만 확인했고 발생 시각은 확인하지 못했다.
- **메모리**: RSS 최대값이 6.0GiB에서 6.6GiB로 조금씩 늘었다. text cache를 1024MiB로 둔 상태이며, 증가가 멈추는지는 더 지켜봐야 한다.

### 4.4 디스크

Go DB의 증가량은 XLog 초당 1.2만 건에서 시간당 약 20GiB였고, 하루치 디렉터리는 275~360GiB였다(XLog·profile gzip 압축 설정 켬). 전환 7일째의 전체 사용량은 약 2.2TiB이며, 이때는 XLog 보관 기간(7일)에 따른 삭제가 막 시작된 시점이라 정상 상태의 값이 아니다. Java DB는 압축 파일시스템 위에 있었으므로 두 값을 직접 비교할 수 없다. 디스크 산정은 [설정 산정](../operations/sizing.md)을 따른다.

## 5. 전환 후 발견한 결함

모두 사전 환경(Agent 약 190개, XLog 초당 약 150건)에서는 닿지 않던 한도와 잠금 경합에서 나왔다. 재현 테스트를 만든 뒤 고쳤고, 사전 환경을 거쳐 같은 binary로 배포했다.

| # | 증상 | 원인 | 수정 | 결과 |
|---|---|---|---|---|
| 1 | UDP datagram 간헐 거부(24분간 8,404건, 유입의 약 0.05%) | Client의 실시간 조회가 object 1건마다 전체 object를 복사하며 수집 잠금을 점유 | 요청한 object만 복사 | 거부 0, 수집 처리 p99 1.2ms → 25µs |
| 2 | 과거 구간 counter 조회 실패와 재시도 집중(CPU 3~4.7 core) | 구간 조회가 전체 object의 기록을 읽어 응답 한도 초과 | 요청한 object만 선별, 선별을 저장 잠금 밖에서 수행, block 단위 읽기 | 1시간 구간 조회 1.6~3.3초 |
| 3 | 5분마다 Agent summary pack 일부 유실 | Agent가 보내는 최대 행 수보다 서버의 목록 한도가 작음 | Agent 기본 최대 행 수를 수신·저장·조회 경로에 일관 적용 | 유실 0 |
| 4 | 매시 같은 시각에 20~40초 동안 UDP 거부 | 호스트가 주기적으로 page cache를 비운 직후, 저장소 잠금 안의 text index 읽기가 디스크로 내려가 수집이 정체 | text 조회에 시간 상한(넘으면 XLog를 group 없이 저장), 메모리 text cache 확대, 압축을 잠금 밖으로 이동, 실패한 재구성의 반복 재시도 제거 | 아래 표 |

결함 4의 수정 전후를, 같은 시각대의 연속한 이틀로 비교했다.

| 시각대 | 수정 전: UDP 거부 / 수집 최대 지연 | 수정 후: UDP 거부 / 수집 최대 지연 | 수정 후 XLog/s |
|---|---|---|---|
| 첫째 | 0 / 174ms | 0 / 50ms | 14.2k~16.3k |
| 둘째 | 57,430 / 230ms | 0 / 53ms | 15.3k~16.4k |
| 셋째 | 176,097 / 257ms | 0 / 51ms | 16.3k~18.5k |

- 수정 전 하루의 UDP 거부는 모두 239,642건이며, XLog로는 약 12만~15만 건(그날 수집량의 약 0.02%)으로 추정한다. 아래쪽은 datagram 대 XLog 비율로, 위쪽은 그 구간의 처리량 감소분으로 계산한 값이다.
- 수정 후에는 page cache가 비워져도 수집이 멈추지 않는다. 대신 그 순간의 XLog 일부가 service group 값 없이 저장된다(관찰값: 한 시간 수집량의 약 0.005%).
- 격리 VM에서 replay 부하 중 page cache를 비우는 방법으로 재현해, 수정 전에는 유실이 나고 수정 후에는 0건임을 확인한 뒤 배포했다.

수정 배포에 따른 재시작은 회당 1~6초의 수신 공백을 만들었다.

## 6. 한계

- 한 환경의 사례다. Agent 구성, profile 크기, text 종류 수, 디스크, 동거 서비스가 다르면 결과가 달라진다.
- Java와 Go를 같은 트래픽으로 동시에 측정하지 않았다. 부하 수준이 달라 CPU는 "더 높은 부하에서 더 적게 썼다"까지만 말할 수 있다.
- 관찰 기간이 짧다(전환 뒤 약 1주). 장기 추세와 연결 수가 크게 다른 조건은 포함하지 않는다.
- 조회 성능은 평시 Client 사용 범위에서만 보았다. 조회 부하를 일부러 올린 시험이 아니다.
- 디스크 사용량은 파일시스템 압축 여부가 달라 비교하지 않았다.
- Java 서버의 유실은 kernel drop 누적과 queue 초과 로그로만 확인했다. 서버가 거부하거나 버린 건수를 Go와 같은 기준으로 세지 못했으므로 유실률을 직접 비교할 수 없다.
