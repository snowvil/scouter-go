## 1. 기존 DB 검사·이관·rollback

원본 계약은 [recovery-retention](../compatibility/recovery-retention.md) §1~§8(코드 판독), Go 결정은 §9다. 원본에는 자동 truncate·rebuild·count 보정이 없다.

| 항목 | 증거 |
|---|---|
| header flush 손실(SIGKILL) | 쓰기 Open이 orphan record를 검증 후 relink한다. Java DB 복사본의 header를 과거로 되돌려 Go로 복구하면 hash/time/TTL hfile이 Java flush header와 **바이트 동일**하고, 원본 reader verify가 PASS다(`TestOriginalJavaStorageInterop`, `TestTTLActualScalaBidirectionalFiles`). 일관성이 깨진 chain(Java 이중 crash)은 Java 의미로 열고 `index-relink-refused`로 보고한다(Java reader `verify-double-crash`와 결과 일치) |

## 3. 성능 baseline (로컬)

도구는 `cmd/scouter-replay`(`make replay`)다. TPS는 **재시작 뒤 TCP 조회로 다시 확인한 고유 XLog 수 / (첫 예정 송신 ~ 서버 종료, drain 포함)**이다. packet·datagram·`Completed` 수와 섞지 않는다. 서버가 UDP queue 포화로 버린 datagram은 `UDP reject`이고, 커널 미수신은 모든 run에서 0이었다.

- payload(seed 42): Java `DataUdpAgent` framing(CAFN 최대 32 Pack/60000B, 초과 시 CAFM). XLog 105~118B, profile 비율 0.3, 크기 분포 0B 10%/1KiB 60%/8KiB 25%/128KiB 5%. text dictionary hit 목표 0.95, error 1%, object heartbeat·counter 각 2초.
- 조회: TCP Client 2개가 1초마다 `TRANX_LOAD_TIME_GROUP`(10초 창, 최대 500)과 realtime cursor를 번갈아 조회한다.
- 서버: `GOMAXPROCS` 2(일부 4), `GOMEMLIMIT` 미설정, 압축 off(일부 on), `--sync-interval` 4s(일부 0). warm-up 3s 뒤 20s steady, soak은 600s.

### 해석과 남은 병목

- 이 호스트·조건에서 누락 없이 처리한 지속 처리량은 20 obj·1000 tx/s(sync off) 수준이다. 200 obj에서는 1000 tx/s부터 reject가 생긴다. `GOMAXPROCS` 2→4는 거의 차이가 없다(단일 Store gate 직렬화).
- 주기 fsync(`--sync-interval` 4s)는 gate 안에서 data·header를 fsync하므로 주기적 stall을 만든다(2000·200: reject 1478 vs 458). macOS `os.File.Sync`는 `F_FULLFSYNC`라 Linux fsync보다 비싸다. 기본값은 내구성을 위해 유지한다.
- gzip 압축 writer는 record마다 32MiB block을 다시 압축하므로 32.5 TPS다. 압축 모드는 고TPS 경로로 쓸 수 없다. 다음 후보는 gzip multi-member append다.
- RSS는 200 obj에서 약 0.8~1.0GiB이며 soak 동안 증가 추세는 없다. visitor HLL(약 280MiB)이 Java와 같은 크기 계약이다.
- soak의 tag top100 cache는 tagcnt 파일이 조회 상한 64MiB를 넘어 생성에 실패한다(5분마다 보고). Client top100 조회 의미에 영향이 있으며 미해결이다.
- 다음 최적화 후보: fsync를 gate 밖으로 옮기기(handle 참조 계수 필요), UDP queue/worker 설정, gate 분할.

**운영 처리량 목표는 측정되지 않았다.** 목표 호스트(공유 자원), 합의된 CPU·메모리 예산, Linux, 실제 Agent corpus, 장시간(2시간 이상) soak, 다수(수백 이상) 연결, Java 원본 동일 조건 비교는 **미검증**이다.

## 5. 독립 리뷰

독립 리뷰에서 나온 항목을 아래와 같이 반영했다. 매 주기 no-op purge, ENOSPC에서 purge 차단, gate 안 대용량 삭제, tag 예산 차감, 이중 crash에서 쓰기 Open 실패 회귀, src torn tail 이관 경로, gzip 고아 block 범위, EIO의 truncated 오분류, eviction Close 실패 시 cache 잔존, inspect fd 상한, visitor 비원자 기록, torn index의 record 검증 누락, trash와 temp 잔여, relink 거부 이벤트 반복, flag 검증.

문서로만 남긴 항목은 두 가지다. ① 전원 손실에서 relink가 data 내구성을 확인하지 않는 한계(G4 한계), ② 주기 fsync stall(위 성능 해석).

## 6. 의도된 차이

- retention은 기본 꺼짐(`--purge`)이다. 후보는 유효한 8자리 날짜만 받는다. 삭제 이력 없이 매 주기 재계산하고, 실패를 보고·재시도한다. pending 집계는 flush 대신 버린다. 대상은 trash로 rename한 뒤 gate 밖에서 지운다.
- 쓰기 Open의 검증된 relink, 참조 없는 torn tail truncate, gzip count 전진. Java는 rebuild하지 않는다.
- SIGKILL 뒤 재기동은 `lock.dat` 5초 규칙으로 약 5초 대기한다. Go writer lock이 더 엄격하다.

## 남은 운영 gate

운영 DB 복사본 이관·rollback 리허설, 전원 손실·disk full 재현, 목표 호스트(Linux, 공유 자원 예산) 지속 부하와 Java 동일 조건 비교, 실제 Agent corpus와 다수 연결, gzip 고TPS writer, tag top100 대용량, 관리 명령 45개·JVM READ 5개·Pulse는 별도 단계다.
