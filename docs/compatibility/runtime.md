# 수집·실행 가능한 서버의 계약

2D 기본 흐름은 `transport → ingest → storage` 수집과 `transport → service → ingest/storage` 조회다. executable은 `cmd/scouter-go`, lifecycle은 `internal/server`가 소유한다. protocol의 Pack 16종 지원과 ingest 지원 범위는 다르다. Object/Text/PerfCounter/XLog/Profile V1·V2와 Alert/Status/Stack/InteractionPerfCounter/Batch/Span/EndUserSummary/KeyValue/DroppedXLog의 수신 의미를 구현했다. MapPack은 조회 payload이며 UDP 수집 대상으로 처리하지 않는다. 세부 저장·cache·discard 계약은 개별 호환성 문서를 따른다.

## 수집과 조회

- Object heartbeat는 receiver 시간을 wakeup으로 사용하고 objHash=0이면 objName의 원본 CRC hash를 계산한다. 신규/날짜 변경/address·type·version 변경 시 저장하고 단순 heartbeat는 cache만 갱신한다. 기본 inactive 판정은 원본처럼 8초, Batch object는 예외다. counter XML family의 master counter를 object tag에 보강한다.
- Text는 receiver 날짜에 저장한다. 영구 dictionary의 빈 text는 원본 writer처럼 생략한다. daily ERROR 빈 문자열은 저장·조회한다. 원본 TextCache가 제공하는 영구 empty의 일시 조회는 현재 Go에서 지원하지 않는다.
- PerfCounter는 packet의 시간을 보존하며 원본 NetDataProcessor처럼 Data에 objHash/time을 주입한다. realtime cache는 최근 값을 유지하고 history는 파일 index로 조회한다. 5분 경계 자동 표본은 최근 numeric/Boolean 값이며 평균을 만들지 않는다. metadata도 일반 counter cache와 동일한 상한을 적용한다.
- XLog는 EndTime=0일 때만 receiver 시간을 적용하고 저장 성공 후 realtime ring에 넣는다. ring은 기본 20,480개다. 완료 XLog와 Pack 수는 서로 다른 지표다.
- Profile은 receiver 날짜와 txid로 저장하며 raw Step chunk 순서를 보존한다. ProfilePack packet의 timestamp로 저장 날짜를 바꾸지 않는다.
- 수집 부수 경로(Java `AgentManager`·`PerfCountCore`·`XLogCore`, 상세는 [ingest CONTRACT](../../internal/ingest/CONTRACT.md)): Kubernetes pod 순번(`PodSeqManager`, `OBJECT_SET_KUBE_SEQ` push), REALTIME `ProcCpu` 초과 시 자동 thread dump(`ObjectCpuChecker`, `TRIGGER_THREAD_DUMPS_FROM_CONDITIONS`), object inactive/재활성/중복 의심 alert(`INACTIVE_OBJECT`/`ACTIVATED_OBJECT`/`MAYBE_OBJ_DUP`), 처음 보는 objType의 counters.site.xml 등록(`addObjectTypeIfNotExist`), WEB/APP_SERVICE XLog의 GeoIP 국가·도시 보강(`GeoIpUtil`, legacy `.dat` reader는 [geoip CONTRACT](../../internal/geoip/CONTRACT.md))을 구현했다. Agent 호출(kube 순번 push, CPU dump)은 수집 경로에서 기다리지 않도록 bounded queue(1024/100)의 worker가 보내며 포화는 `Dropped`로 센다. 기동 30초 뒤와 날짜 변경 시 live agent에 `OBJECT_RESET_CACHE`를 보내 text 재전송을 유도한다(Java `TextCacheReset`). Java는 Agent마다 순서대로 최대 so_timeout(60초)씩 기다리지만, Go는 Agent 간 독립이므로 최대 16개(Go 전용 `go_text_cache_reset_parallel`, 1..64, live)를 동시에 호출하고 호출마다 별도 대기 상한 없이 relay deadline(so_timeout+`RequestTimeout`)까지 답을 기다린다(2026-10-23, 이전 Go는 순차 5초 후 고아 relay). 느린 Agent가 뒤 Agent의 reset을 늦추지 않고, pass가 고아 relay slot을 쓰지 않는다. relay 메모리 예산이 차 있으면 기다리지 않고 그 Agent를 나중에 다시 부르며, 재시도 횟수에는 넣지 않는다(pass 요약의 `refused`). Agent별 실패 줄은 10초에 1줄(생략 수 포함)이고 pass 끝 요약 줄이 모든 실패를 센다.

현재 object/cache/counter 상한의 기본값은 각각 16,384개/64MiB/262,144개(`internal/ingest/engine.go` `DefaultMaxObjects`·`DefaultMaxCacheBytes`·`DefaultMaxCounters`, `--max-objects`·`--engine-cache-mb`·`--max-counters`로 변경)이며 설정 타입과 byte budget을 검사한다. 이는 Go heap/RSS 상한이나 운영 자원 예산의 보장이 아니다. 저장 파일·index·daily table cache도 유한하게 유지하고 eviction 시 sync/close한다. 조회의 취소는 gate 대기, scan callback, decode 및 gzip block 읽기에 반영한다. 일반 파일 syscall 자체를 강제로 중단하지는 않는다.

기본 명령과 response body/empty/cursor 계약은 [query-contract.md](query-contract.md), 파일 형식은 [storage-contract.md](storage-contract.md)를 따른다. 날짜는 Java 고정 24시간 기준 계산이며 일반 DST 현지 자정 계산과 다를 수 있다.

## 실행 설정

```sh
make build
./dist/scouter-go --db ./database --udp 127.0.0.1:6100 --tcp 127.0.0.1:6100 --timezone Asia/Seoul
```

원본 default `counters.xml`을 변경 없이 embed하고 `counters.site.xml`(custom)은 `internal/counters`가 Java JAXB 정규화와 동일하게 관리한다. 계정 관리·LDAP는 `--account-dir`로 지원한다. 계정 파일 모드는 Java처럼 받은 `pass` 문자열을 그대로 비교하고, `--user/--password` 단일 credential 모드는 salted SHA-256만 받으므로 raw(secureLogin=false) login을 지원하지 않는다. GeoIP는 `geoip_data_city_file`(기본 `./conf/GeoLiteCity.dat`, 작업 디렉터리 기준)을 기동 때 열고 없으면 끈다. 값이 바뀌면 settings owner goroutine이 다시 연다(실패하면 이전 DB 유지). `SERVER_STATUS`는 Go HeapAlloc/HeapSys를 반환하므로 JVM heap 의미와 다르다. login response에는 credential을 반환하지 않고 미지원 관리 권한은 false로 설정한다.

## 종료와 writer 배타성

SIGINT/SIGTERM/SIGHUP(기동 시 이미 ignore 상태면 SIGHUP은 계속 무시), 종료 파일 삭제, 콘솔 `quit`은 모두 같은 graceful 종료 경로다. SIGQUIT(`kill -3`, 콘솔 raw mode의 Ctrl-\ 포함)은 JVM thread dump처럼 goroutine dump를 stderr에 쓰고 **서버는 계속 실행**한다(Go 기본의 dump 후 exit 2가 아님). 기동 중 실패하면 runtime·profile·server log를 같은 경로로 닫고 종료한다. 수신과 handler를 종료·join하고 engine을 닫은 뒤 counter/store를 sync/close한다. 그동안 독립 goroutine의 `lock.dat` heartbeat를 유지하고 마지막에 heartbeat와 writer lock을 해제한다. heartbeat는 `-console` 모드에서도 유지한다(Java 콘솔 모드에는 heartbeat가 없다, [recovery-retention](recovery-retention.md) §6). Go writer끼리는 `flock`으로 격리한다. Java의 `lock.dat` 5초 stale 규칙에도 참여하며 최초 생성은 exclusive create, 삭제는 소유한 inode만 대상으로 한다.

**종료 상한(Go 전용).** 원본 Java는 shutdown hook에 상한이 없고, 운영 스크립트(`scripts/scouter-go.sh stop`)는 SIGTERM 30초(`SCOUTER_STOP_TIMEOUT`) 뒤 SIGKILL한다. Go는 그보다 먼저 스스로 끝낸다.

- **상한**: 종료가 시작되면 `--shutdown-timeout`(기본 20초)을 잰다. 시작 조건은 첫 신호, 종료 파일 삭제, 콘솔 `quit`, listener·heartbeat 실패로 `Run`이 스스로 정리를 시작한 경우다.
  - `scripts/scouter-go.sh`는 `SCOUTER_STOP_TIMEOUT`이 설정돼 있으면 `max(SCOUTER_STOP_TIMEOUT − 10, 5)`초를 넘긴다. `SCOUTER_EXTRA_ARGS`에 직접 준 값이 우선한다([runbook](../operations/cutover-runbook.md) §9).
  - 안쪽 단계의 개별 상한: `Engine.Close`는 deferred 쓰기 제출 5초, writer drain 5초, 갇힌 writer 1초로 최악 11초다. SQL table은 5초, Pulse dispatcher·producer는 각 5초다. 합하면 26초이고, `Counters.Close`·`Store.Close`에는 자체 상한이 없다. 그래서 20초는 여러 단계가 동시에 멈출 때만 넘는다.
  - 부하 중 측정(2026-10-24, 개발 노트북 macOS, 8 CPU를 다른 작업과 공유, 기본 GOMAXPROCS, `--sync-interval` 기본 4초, 비압축). `scouter-replay` 외부 모드로 15,000 XLog/s를 보냈다. 조건은 objects 50, senders 4, 기본 profile 분포, 조회 2개 병행이다. 20초째(XLog 약 29–30만 건, profile 약 8만 건) SIGTERM에서 종료까지 1.095s, 1.002s, 1.017s였다. 세 번 모두 exit 0, `.go-clean`, queue 잔여 0이었다. 운영 예측치가 아니다. 느리지만 정상인 종료가 20초에 닿는 근거는 찾지 못했으므로 기본값을 유지한다.
- **넘으면**: 멈춘 단계와 남은 queue를 한 줄 로그하고 **exit 3**으로 끝낸다.
  - `.go-clean`은 `Store.Close`가 이미 써 둔 경우에만 남는다. 줄의 `marker=written|absent`가 그 여부를 바로 보여 준다. 대략 `stage`가 `writer lock`·`closed`이거나 `store/checkpoints`, 또는 `main`이 `mode stop`·`config watch`·`finish`이면 written이다.
  - marker가 없으면 다음 기동은 crash checkpoint(`.go-checkpoint`)로 index 꼬리를 검증·복구한다. SIGKILL과 같은 경로다([recovery-retention](recovery-retention.md) G7).
  - 줄 형식: `shutdown: budget 20s exceeded; exiting 3 stage="store/sync" elapsed=20.001s ingestPending=12(counter:10 daily:2) xlogQueue=0 profileQueue=0 marker=absent pulseQueue=0/0 kafkaPending=0 main="run"`.
  - `stage` 순서: `listeners` → `background`(주기 sync·purge·visitor/tag flush·tick·agent 호출 goroutine 종료 대기) → `final stats`(최종 계수 줄. visitor 통계가 visitor 쓰기를 기다리면 여기서 멈춘다) → `http` → `listener close` → `ingest writers` → `sqltable` → `pulse` → `counters` → `store`(하위 단계 `xlog writer`·`profile writer`·`text writers`·`gates`·`sync`·`visitor flush`·`index close`·`clean marker`·`checkpoints`) → `writer lock` → `closed`. `main`은 `Run`이 반환된 뒤 main이 멈춘 곳이다(`mode stop`, `config watch`, `finish` = profile·server log 닫기).
  - `ingestPending`은 kind별 ingest writer에 남은 record, `xlogQueue`/`profileQueue`는 storage writer queue 길이, `pulseQueue`는 dispatcher의 XLog/profile 대기, `kafkaPending`은 producer 버퍼다. 뒤의 둘은 Pulse가 켜졌을 때만 나온다.
  - 강제 종료는 run mode의 정리를 기다리지 않는다. 대신 짧은 정리를 보고 줄 쓰기와 함께(병렬) 한다. 콘솔 모드는 terminal 속성을 복구하고, 일반 모드는 `<pid>.scouter`를 지운다. 정리가 막혀도 보고 줄은 먼저 남는다.
  - 보고 줄은 log package를 거치지 않고 stderr와 server log에 직접 쓴다. 정리와 보고·flush를 합쳐 최대 2초 기다린다. 디스크나 tty가 멈춰 그 사이 끝나지 않으면 보고 줄이 남지 않을 수 있지만, 그래도 exit 3으로 끝낸다.
- **이후 신호**: SIGINT/SIGTERM이 **첫 신호보다 1초(`signalDupWindow`) 넘게 늦게** 오면 `shutdown: second signal SIGTERM; exiting now stage=...` 한 줄을 남기고 바로 끝낸다. exit code는 128+신호 번호(SIGINT 130, SIGTERM 143)이고 marker는 남기지 않는다(`marker=` 표시는 위와 같다).
  - 1초 안의 반복(Ctrl-C가 wrapper와 서버에 함께 전달되는 경우 등)은 로그만 남기고 무시한다.
  - 종료 파일 삭제·콘솔 `quit`·`Run` 자체 정리 뒤 처음 온 신호는 첫 신호로 다룬다. 예를 들어 그 뒤의 `scouter-go.sh stop`은 graceful 종료를 그대로 둔다.
  - SIGHUP은 강제 종료를 하지 않는다. terminal hangup은 여러 번 전달될 수 있다.
  - 이전에는 `signal.NotifyContext`가 두 번째 신호를 삼켰다.
- **첫 신호**: `shutdown: SIGTERM received; graceful shutdown within 20s (SIGINT/SIGTERM again after 1s exits at once)` 줄을 남긴다. 상한이 0이면 `graceful shutdown, no shutdown budget (...)`이다. 신호 goroutine은 먼저 cancel과 상한 시작을 하고, 로그 줄은 기다리지 않고 log goroutine 하나에 넘긴다(대기 8줄). 그래서 stderr가 막혀도 신호 처리가 멈추지 않는다. 대기가 차면 줄을 버리고 세며, 버린 수는 다음 줄에 `(N earlier shutdown log lines dropped)`로 붙는다.
- **ingest writer**: `Engine.Close`의 5초 상한 뒤 context를 보지 않는 호출(멈춘 디스크)에 갇힌 writer는 1초(`writerStuckGrace`)만 더 기다리고 남긴다.
  - 그 kind의 남은 record는 `Pending`으로 남고 `ingest: <kind> writer still in a write ... N records left pending` 줄이 나온다. 이전에는 그 writer를 무한히 기다렸다.
  - runtime은 이때 `Store.SkipCleanMarker()`를 불러 counters·store를 닫되 `.go-clean`은 쓰지 않는다(`WARNING: ingest writers still hold N records: the clean-shutdown marker is not written`). 상한이 0이어도 같다.
  - 남은 쓰기는 storage gate를 거쳐야 하므로, 닫힌 뒤에 돌아오면 `ErrClosed`로 실패한다. 진행 중 record는 취소된 context로 실패한다([ingest CONTRACT](../../internal/ingest/CONTRACT.md) §13).
- 검증(`cmd/scouter-go`):
  - `TestShutdownBudgetEndsStalledStage`: `background`·`ingest writers`·`store`·`store/sync` 단계를 context 없이 멈춘 subprocess. exit 3, `marker=absent`, 종료 파일 삭제를 확인한다. 수정 전에는 15초 뒤에도 실행 중이었다.
  - `TestSecondSignalExitsAtOnce`(수정 전 실패), `TestFirstSignalAfterExitFileIsGraceful`, `TestBudgetWithoutSignal`(종료 파일·콘솔 quit·heartbeat 실패), `TestZeroBudgetWaits`.
  - `TestStuckWriterStillClosesStore`: object writer가 갇혀도 store까지 닫고 exit 0, marker 없음.
  - `TestCleanShutdownWritesMarker`.
  - `TestRestartAfterForcedShutdownRecovers`: `store` 단계와 `Store.Close`의 `index close` 도중 강제 종료. 재기동이 marker 없이 `Checkpointed`로 열고 두 run의 XLog를 유지한다.
  - `shutdown_guard_test.go`: 막힌 로그, 다른 trigger 뒤 첫 신호, 1초 안 반복, SIGHUP, 상한 0. 이 다섯은 수정 전 실패였다(상한 0은 `within 0s` 문구). 막힌 정리에서도 보고 줄이 남는지(`TestGuardStuckAbortStillReports`), 로그 대기 상한과 버린 수 표시(`TestGuardLogLinesBounded`)도 본다.
  - 남은 위험: 콘솔 raw mode 복구는 실제 tty에서 검증하지 않았다. 또 신호 처리 시작부터 run mode 정리 등록(`setAbort`) 사이의 짧은 구간에 강제 종료되면 종료 파일과 terminal 정리를 건너뛴다.
  - 그 밖에 `internal/ingest` `TestCloseDeadlineLeavesAStuckWriter`(수정 전 실패), `internal/storage` `TestSkipCleanMarker`.

원본 stale 규칙은 엄격한 분산 lock이 아니다. 장시간 filesystem stall이나 process 정지 뒤의 Java 재기동까지 안전하게 fencing하지 못한다. **Java와 Go를 같은 DB에 동시에 쓰지 않는다.** 운영 DB는 이관·rollback gate 전에는 입력으로 사용하지 않는다.

Pulse가 켜지면 ingest는 Java `XLogCore`/`ProfileCore`가 `PlugInManager`를 부르는 지점(저장 직전)에서 dispatcher에 non-blocking offer만 하고, 변환·필터·JSON·Kafka enqueue는 dispatcher worker가, 전송은 producer goroutine이 맡는다. 종료 시 engine → dispatcher drain → producer drain 순서이며 잔여는 `ShutdownDiscarded`/`kafkaAbandoned`로 센다. 종료 로그에 `pulse=… kafka=…` 통계 줄이 추가된다.

주기 sync와 retention은 수집 goroutine 밖의 maintenance goroutine이 실행한다. 둘 다 storage gate를 잡으며, 실패는 로그로 남기고 `maintenanceErrors`로 계수한 뒤 다음 주기에 재시도한다. 자동 crash 복구([recovery-retention](recovery-retention.md))는 `storage recovery` 로그와 `recoveries`로 남긴다. UDP는 종료 시 queue에 남아 처리하지 못한 datagram을 `ShutdownDiscarded`로 따로 센다. `Rejected`는 크기 초과와 serving 중 queue 포화만 뜻한다. fragment 재조립 상한 초과는 `AssemblyRejected`로 세며 `Malformed`에 넣지 않는다(2026-10-23).

오류 callback은 64개 bounded channel에 전달하고 포화 시 별도 계수한다. transport의 `tcp.connection` 오류는 사유 분류(timeout·closed·limit·unsupported·unauthorized·other)마다 10초에 한 건만 보내고, 그 사이 생략한 수를 다음 건에 `(<n> more <분류> errors since the last line)`으로 붙인다. 정확한 합계는 `/health` `tcp.Errors`, 분류별 누적은 `tcp.TimeoutErrors`·`ClosedErrors`·`LimitErrors`·`UnsupportedErrors`·`UnauthorizedErrors`·`OtherErrors`다. logger는 초당 한 건만 제한된 길이로 기록한다. 종료 로그에는 ingest/UDP/TCP 통계와 deferred/dropped error log 수를 남긴다. UDP application 수락·저장 완료는 durable fsync나 손실 없는 전달의 증거가 아니다.

### 운영자 안내: 3C에서 바뀐 동작

- **Client idle 종료 8초**: Client TCP 연결은 `net_tcp_client_so_timeout_ms`(기본 8000ms) 동안 명령이 없으면 서버가 닫는다(Java와 같음, 이전 Go는 60초). Scouter Client는 2초마다 `CHECK_JOB`을 보내므로 영향이 없다. 8초보다 긴 간격으로 폴링하는 TCP Client API 소비자(자체 수집 스크립트 등)는 끊긴 뒤 재연결하도록 하거나 이 키를 늘린다. `scouter-replay`는 idle 종료 뒤 조용히 재연결한다. 값은 새 연결부터 적용된다.
- **Client service pool**: 동시에 명령을 처리하는 Client 세션은 `net_tcp_service_pool_size`(기본 100)로 제한된다. 넘는 Client는 so-timeout(기본 8초)까지 기다린 뒤 닫히고, 대기자가 `max(1, --max-connections/2)`를 넘으면 바로 닫힌다. 대기 중 연결을 끊은 Client의 명령은 나중에 실행하지 않는다. 포화는 stats 줄의 `waiting`/`wait-timeout`/`wait-reject`와 10초 1회 Go 전용 로그 줄로 보인다. Client·webapp 동시 사용이 많으면 이 값을 올리고(재기동 없이 반영) `--max-connections` 안에 둔다.
- **Client 응답 메모리 예산**(2026-10-23): encode한 Client 응답 item 중 64KiB 이상인 것은 모든 Client 연결이 함께 쓰는 byte 예산을 잡고 socket에 넘긴 뒤 반납한다. 기본은 GOMEMLIMIT이 있으면 그 1/4(최소 item 하나 257MiB), 없으면 1GiB다. 예산이 차면 그 item은 연결의 pool 대기 상한(client so-timeout, 최대 `RequestTimeout`)까지 기다리고, 그래도 자리가 없거나 대기 중 item 합이 예산을 넘으면 그 명령만 실패한다(연결 종료, item 하나 상한 초과와 같은 동작). Java Client는 소켓을 닫고 그때까지 받은 item만으로 오류 표시 없이 정상 반환하므로 결과가 비거나 잘려 보이고, 다음 명령에 재연결한다(Java 서버는 handler 예외 뒤에도 NoNEXT를 쓰고 연결을 유지한다). 작은 응답과 Agent Blob relay chunk(heap dump 등, relay 예산이 따로 셈)는 영향이 없다. `/health` `tcp`의 `ClientResponseBytes`·`ClientResponsePeakBytes`·`MaxClientResponseBytes`·`ClientResponseWaiting`·`ClientResponseWaits`·`ClientResponseRejected`와 10초 1줄 로그로 확인한다. 크기는 Go 전용 `go_client_response_budget_mb`(MiB, 257..1048576, 재기동)로 바꾼다([config CONTRACT](../../internal/config/CONTRACT.md) §6).
- **Agent relay 메모리 예산**(2026-10-23): Client 요청·text cache reset·수집 부수 호출이 Agent에 보내는 모든 relay는 명령을 쓰기 전에 전역 byte 예산(Client 응답 메모리 예산과 같은 규칙: GOMEMLIMIT이 있으면 그 1/4, 없으면 1GiB, 하한 768MiB = 큰 relay 2개 512MiB + 일반 relay 32개 256MiB, 첫 relay 때 한 번 정함)에서 그 relay가 가질 수 있는 최대 byte(일반 8MiB, `OBJECT_THREAD_DUMP`·`OBJECT_HEAPHISTO`·`OBJECT_DOWNLOAD_JAR` 256MiB, Blob stream은 chunk 하나 16MiB)를 잡고 읽기가 끝나면 돌려준다. 256MiB relay는 동시에 2개까지다. 고아 relay는 자기 relay의 예산을 그대로 들고 있으며 고아 byte 상한(512MiB)은 이 예산 안의 몫이다(이중 계상 없음). Java에는 없는 상한이다. Go 전용 `go_agent_relay_budget_mb`(크기, MiB 768..1048576), `go_agent_relay_max_large`(큰 relay 동시 수, 1..64), `go_agent_relay_server_wait_ms`(서버 발신 호출 대기, 1..60000ms)로 재기동 없이 바꾼다. 줄이면 들고 있는 permit은 그대로 두고 새 relay부터 거절한다.
  - 예산이 차 있을 때의 대기는 보내는 쪽에 따라 다르다. Client 명령의 relay는 예산 대기와 그 뒤의 Agent 세션 대기를 합쳐 live `net_tcp_get_agent_connection_wait_ms`(기본 1초, Java `RequestQueue.get` 대기와 같은 값) 한 번만 기다린다(이전에는 두 대기가 각각 이 값만큼 걸릴 수 있었다). 이 대기는 `AwaitUpstream` 안에서 일어나므로 그동안 Client가 연결을 닫거나 RST를 보내면 transport probe가 명령 ctx를 끝내고, Client가 떠난 뒤에 명령이 Agent로 가는 일은 없다. FIN·RST 없이 끊긴(half-open) Client는 TCP keepalive나 대기가 끝날 때에야 알아챈다. 그 안에 자리가 나지 않으면 보내지 않고 Java `AgentCall` null과 같은 결과(단일 대상은 응답 없음, fan-out은 다음 Agent로)를 준다. 한 명령에서 한 번 거절되면 같은 명령의 나머지 relay는 기다리지 않으므로, fan-out(예: `OBJECT_ACTIVE_SERVICE_LIST_GROUP`)의 추가 대기는 Agent 수와 무관하게 최대 1회다. 대기열에 있는 서버 발신 호출(kube 순번 push, CPU thread dump trigger)은 10초 기다리고, 거절되면 실패(`agentcall.*.failed`)로 센다. text cache reset은 기다리지 않는다. 거절되면 그 Agent를 10초 뒤 다시 부르며 재시도 횟수에 넣지 않는다. 따라서 reset이 Client relay 몫을 오래 차지하지 않는다.
  - 거절된 relay는 Agent에 아무것도 보내지 않고 세션도 잡지 않는다. `/health`의 `agentRelayBudget`(`Bytes`·`Limit`·`Large`·`MaxLarge`·`Waiting`·`Granted`·`Waited`·`Refused`·`LargeRefused`·`ServerRefused`)과 분당 1줄 로그로 확인한다.
  - 기본값 근거: GOMEMLIMIT이 없으면 Client service pool 100 + text cache reset 16 + 수집 호출 몇 개 ≈ 120 × 8MiB를 받도록 1GiB로 정했다. 큰 relay 2개(512MiB)가 돌 때도 나머지 절반이 남는다. 하한 768MiB는 큰 relay 2개와 일반 relay 32개를 늘 보장하는 값이다. 그래서 GOMEMLIMIT이 3GiB보다 작으면 예산이 그 1/4보다 크다. 예를 들어 2GiB 한도에서 relay 768MiB와 Client 응답 예산 512MiB를 합하면 약 1.25GiB다. 이런 작은 한도에서는 Client 사용 규모에 맞춰 GOMEMLIMIT을 정한다.
  - 예산은 wire byte 기준이다. V2 응답은 decode하는 동안 body와 decode 결과를 함께 들고 있어 실제 peak는 최대 약 2배다. Agent 응답 decode 뒤의 Client 응답 encode는 위 Client 응답 메모리 예산이 따로 센다.
- **visitor 메모리 예산**(2026-10-24): 통째로 메모리에 두는 visitor HLL(resident, 기본 256MiB)과 flush를 기다리는 register(delta, 기본 64MiB)의 예산은 Go 전용 `go_visitor_resident_mb`(MiB, 1..16384)와 `go_visitor_delta_mb`(MiB, 16..1024)로 재기동 없이 바꾼다. Java에는 이 키가 없다. Java는 dense HLL을 entry 상한(500)까지 둔다. resident 예산을 줄이면 다음 적용 시점(방문, roll tick, `FlushVisitorsIfDue`. 보통 1초 이내)에 오래 안 쓴 entry부터 partial로 강등한다. 강등하면 delta 예산을 넘게 되는 dirty entry는 다음 pass가 쓴 뒤 강등한다. 늘리면 다음 flush pass부터 승격한다. delta 예산을 지금 delta보다 작게 바꾸면 flush를 바로 due로 표시한다. 어느 쪽이든 방문은 잃지 않고 파일 bytes도 같다. 바뀌는 것은 메모리와 flush·realtime 조회의 IO다. 크게 줄일 때는 단계적으로 줄인다. 강등하면 delta 예산을 넘게 되는 dirty entry는 flush pass가 쓴 뒤 강등한다. 그래서 그 entry가 쓰이고 강등될 때까지(쓰기가 실패하면 10초마다 재시도) resident가 예산을 넘는다. 넘는 양은 resident entry 수 × 약 683KiB 이하다. 적용은 다음 방문이나 tick 때이고, `/health`를 읽을 때도 적용된다. 적용 값은 `/health` `visitors`의 `ResidentMax`·`DeltaMax`, 수집 경로의 바로 쓰기는 `WriteThroughs`로 본다. 세부는 [storage CONTRACT](../../internal/storage/CONTRACT.md) §8 visitor, 범위 근거는 [config CONTRACT](../../internal/config/CONTRACT.md) §6에 있다.
- **HTTP admission**(2026-10-23): Java `HttpServer`는 Jetty 9.4.6 기본값(`QueuedThreadPool` 최대 200 thread, 상한·대기 시간 없는 job queue, 연결 수 상한 없음, idle 30초)이라 넘치는 요청은 무한히 기다린다. Go는 상한을 두고 넘치면 `503`+`Retry-After: 1`로 답한다(의도된 차이). 아래 수치는 Go 전용 `go_http_max_connections`·`go_http_servlet_max_inflight`·`go_http_servlet_queue_wait_ms`·`go_http_webapp_max_inflight`·`go_http_webapp_queue_wait_ms`·`go_http_ops_max_inflight`로 바꾼다(재기동, servlet 동시 수 1..1024, webapp 1..256, 대기 1..60000ms. 연결 상한은 아래 open file 한도 맞춤이 여전히 적용되며 명시한 값이 낮춰지면 로그를 남긴다). 범위 근거는 [config CONTRACT](../../internal/config/CONTRACT.md) §6.
  - listener마다 연결 수 상한: 1024. open file 한도가 낮으면 `DB 예비분/4 − 64`로 낮추며 최소 192다(예비분 ≥ 1024). 넘는 연결 64개까지는 받아서 `503`+`Connection: close`로 답하고(`/health`·pprof는 그 연결에서도 응답), 그것도 차면 응답 없이 닫는다. listener 2개의 연결과 over-limit 연결을 합해도 예비분의 절반을 넘지 않는다.
  - 상한의 7/8 이상이 열려 있으면 모든 응답에 `Connection: close`를 붙인다(`KeepAliveClosed`). 그래서 keep-alive로 연결을 붙잡고 있던 push 호스트(Telegraf, `/counter`)가 flush 사이에 slot을 비운다. push 호스트 수와의 관계는 이렇다. 호스트 수가 상한의 7/8 이하이면 각자 keep-alive 연결을 유지한다. 그보다 많으면 flush마다 다시 연결하고, 동시에 열린 요청이 상한보다 적은 한 모두 받아진다. 상한이 192인 호스트에서 Telegraf 수백 대가 동시에 flush하면 일부가 503을 받고 다음 flush에 다시 보낸다. 그런 규모면 `ulimit -n`을 올린다.
  - servlet(`/counter`, `/register`, `/telegraf`, ingest engine lock을 잡는 요청): 동시 64개, 빈자리를 최대 3초 기다린 뒤 503(`scouterHttp`의 `Busy`·`Waited`·`Abandoned`·`InFlight`).
  - webapp(`/scouter/*`): 동시 64개, 최대 3초 대기 뒤 503.
  - 대기 3초는 client 자신의 timeout(Telegraf `outputs.http` 기본 5초, Scouter Client 8초)보다 짧게 정했다. 대기 중인 요청은 body를 읽기 전이라 client가 떠난 것을 알 수 없으므로, 더 길게 기다리면 client가 이미 재전송한 요청을 중복 처리할 수 있다.
  - `/health`·`/debug/pprof`: 위와 별도의 동시 16개 예산(대기 없음)이라 servlet·webapp 폭주와 무관하게 응답한다.
  - `/health`의 `httpAdmission`(`http`·`scouterHttp` listener별 연결 수·상한·`OverLimit`·`ClosedAtAccept`·`OverLimitRejected`·`Operational`, `webapp` gate)과 사유별 분당 1줄 로그로 확인한다. 대기는 client가 끊으면 끝나며(`Abandoned`) 연결 상한이 대기 요청 수도 제한한다.
- **TCP 연결 예산**(2026-10-21): handshake, Agent, Client 예산을 따로 센다. 상한에 걸린 연결은 아무것도 읽거나 쓰지 않고 즉시 닫힌다. Agent에는 서버가 잠시 내려간 것과 같아서 1초 뒤 다시 접속하고, 애플리케이션 thread는 영향을 받지 않는다.
  - 상한 도달은 사유별로 10초에 한 줄씩 로그에 남는다. 줄에는 peer, Agent objHash(이미 받은 경우), 현재 수/상한, 올릴 flag가 들어가고, 그 사이 거절 수도 "N more rejected"로 누적된다.
  - `/health`의 `tcp`에 `HandshakeRejected`·`AgentRejected`·`ClientRejected`와 현재 연결 수, 상한이 있다.
  - descriptor 부족(EMFILE 등)으로 Accept가 실패하면 TCP 서버를 멈추지 않고 5ms~1초 backoff 뒤 다시 받는다(`AcceptRetries`, 10초에 한 줄 로그). 세 예산의 합과 저장 파일 수보다 `ulimit -n`을 넉넉히 둔다.
- **server log 파일**: `log_dir`에 `server-yyyyMMdd.log`·`request-yyyyMMdd.log`가 생기고 `log_keep_days`(기본 31) 지난 파일은 1시간 주기로 지운다. stderr(실행 스크립트의 로그 파일)에도 같은 줄이 계속 나온다.
- **SIGQUIT**: `kill -3`은 goroutine dump를 stderr에 남기고 서버를 멈추지 않는다.
- **종료 파일**: 일반 모드는 작업 디렉터리에 `<pid>.scouter`를 만든다. 지우면 서버가 정상 종료한다(위 flag 표).
- **webapp**: collector 연결 pool의 idle timeout 기본이 8초(`net_tcp_client_so_timeout_ms` 파생)이며, idle 뒤 끊긴 연결은 응답 byte 전 EOF/reset이면 새 연결로 1회 다시 보낸다(요청 쓰기 실패는 항상, 그 밖에는 SET_/SAVE_ 계열·`OBJECT_REMOVE_INACTIVE`·`OBJECT_THREAD_CONTROL`·`OBJECT_HEAPHISTO`를 뺀 명령만).

제외 확정(명시적 미지원): JVM 스크립트·plugin 실행(`.alert` 규칙 컴파일·실행, `.plug`, plugin JAR, MapPack·standalone SpanPack 등 확장 handler chain), webapp의 extweb·swagger·WebSocket `/basic`·webroot·`/v0/temp/test/*`. `.alert`/`.conf` 저장·조회와 descriptor 응답은 지원한다.

그 밖의 한계: `SERVER_STATUS`·`SERVER_THREAD_*`·`SERVER_ENV`는 JVM이 아니라 Go runtime 값을 보인다. 현재 gzip writer는 record마다 member를 append하므로 고TPS 압축 경로는 별도 측정 대상이다([storage-contract](storage-contract.md)). Unix `flock`·termios 기반 구현은 Windows 실행을 검증하지 않았다. 운영 DB 이관·전환과 공유 호스트 부하 검증은 남은 gate다.

실제 Java 통신 클래스의 synthetic 수집·조회·재시작 검증은 [harness 범위](../../tools/java-integration/README.md)를 따른다. 실제 `-javaagent` Java Agent와 Host Agent 상호운용은 [java-agent-interop](../validation/2026-10-24-java-agent-interop.md)에서 확인했다. 전체 Eclipse RCP 화면, 전체 Host OSHI sampling, 운영 부하와 장애복구는 별도 gate다.
